### Список требований к внешним системам
1. Биометрия/информация об авто номерах должна обрабатываться и храниться на стороне партнёра, который предоставляет сервис интеллектуального домофона/шлагбаума.
2. Партнер хранит:
    Данные об номерах/лицах
    Обрабатывает распознавание номеров/лиц
    Отдает обезличенный результат propDevelopment, в виде факт события, условно пользователь 123 успешно идентифицирован/шлагбаум открыт
3.  PropDevelopment передаёт только ID пользователя и его разрешения на доступ к домофону/допуску автомобиля.
4. В PropDevelopment хранятся только:
   	ID пользователя, список разрешённых точек доступа (подъезд, шлагбаум), логи: «распознан», «отказано», «открыто».

### Требования к формату передачи данных.
1. Никаких персональных данных, только тонизированные.
2. Шифрованный канал передачи данных использование TLS1.3 HTTPS. 
Обязательная верификация отправленных и полученных данных, что в процессе не были изменены. Через цифровые подписи/хэш суммы.
3. Никаких открытых ключей/токенов в запросах. Использовать защищённые сессии.
4. Ограничение IP(белые адреса) или VPN-туннель между PropDevelopment и платформой партнёра.
5. Ведение журнала всех запросов (audit logging)
6. Использовать авторизацию и аутентификацию для внешних сервисов OAuth 2.0
7. JWT с утверждёнными claim
8. Интеграция с IAM PropDevelopment для проверки прав доступа
9. Возможность отзыва токенов и принудительного завершения сессий

### Организация взаимодействия между системами
1. Через отдельный API-шлюз (gateway), чтобы разграничивать доступ и централизованно управлять политиками 
 безопасности(в схеме не отобразил), но подразумеваем что так должно быть, 
 не хотелось всю схему перерисовывать через api gateway, особенно не понимая что в облаке, а что на земле.
2. REST API (или gRPC, если необходима высокая производительность)
3. Retry-логика и Circuit Breaker в случае отказа стороннего API
4. Единая система мониторинга может Grafana если уже есть.
